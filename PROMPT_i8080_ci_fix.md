# ПРОМПТ ДЛЯ КОРРЕКТИРОВКИ i8080_ci (ci-app / assemble8080)

## Контекст
i8080_ci — двухпроходный ассемблер Intel 8080/8085 + линкер (Python, пакет `assemble8080` в `ci-app`).
Пайплайн SmallC: `.c -> cc8080.exe -> .s -> ci-ассемблер (--obj, --cpu 8085) -> .obj (i8080-obj-v1) -> ci-линкер -> .bin -> run8080.py`.
Состояние: ci-app на чистом коммите `c885b1e`. Полный прогон 97 тестов даёт **87/97**. Ниже — баги, которые живут именно в i8080_ci (не в компиляторе cc8080 и не в рантайме).

---

## БАГ #1 (КРИТИЧЕСКИЙ): неверный размер ALU-команд с immediate в pass 1

### Суть
В pass 1 (расчёт смещений символов) размер инструкции берётся напрямую из таблицы `MNEMONICS`:

```python
# assemble8080/assembler.py, ~строки 911-915 (pass 1)
_mnemonics = self._get_mnemonics()
if mnemonic in _mnemonics:
    opcode, fmt, size = _mnemonics[mnemonic]
    location += size          # <-- BUG: size не зависит от операнда
    self.pc = location
```

Для ALU-команд формата `r` (регистр) в таблице `size = 1`. Но когда операнд — **немедленный** (не регистр), реальное кодирование **2 байта**:

| Mnemonic | reg-форма (1 байт) | imm-форма (2 байта) |
|----------|-------------------|---------------------|
| ADD      | 0x80+r            | 0xC6 xx             |
| ADC      | 0x88+r            | 0xCE xx             |
| SUB      | 0x90+r            | 0xD6 xx             |
| SBB      | 0x98+r            | 0xDE xx             |
| ANA      | 0xA0+r            | 0xE6 xx             |
| XRA      | 0xA8+r            | 0xEE xx             |
| ORA      | 0xB0+r            | 0xF6 xx             |
| CMP      | 0xB8+r            | 0xFE xx             |

Регистры-операнды: `A B C D E H L M` и пары `BC DE HL PSW`. Всё остальное (число, `#n`, метка, выражение) = immediate = 2 байта.

### Последствия
Pass 1 занижает смещение на 1 байт за каждую такую инструкцию. Ошибка **накапливается** по всему модулю, и все символы, объявленные после первой ALU-imm инструкции, получают неверный offset. В pass 2 эти (неверные) offsets используются для:
- вычисления адресов меток,
- генерации relocation,
- бейки SAME-module ссылок как ABSOLUTE.

Итог: код ссылается на адреса, сдвинутые на N байт -> вызовы попадают в середину чужих функций -> мусор / зависание.

### Воспроизведение
- Тест `t27` (есть ALU-imm в теле): exit=1, ожидается 0.
- Тест `t24` (long long 64-bit): exit=127, зависает на PC=0x0038 (RST7). Причина — рантайм-объект `test_crun.obj` собран этим же (баговатым) pass 1, поэтому смещения `ccadd64/ccpop64/ccgllong/...` сдвинуты, и `call` попадает не в ту функцию.
- Диагностика (ранее): `CCPOP64` symbol offset=0x04ac, а реальный паттерн `E1` (POP H) на 0x04b2 — сдвиг 6 байт = 6 ALU-imm инструкций до него.

### Фикс (pass 1)
Перед `location += size` добавить проверку: если `fmt == 'r'` и операнд НЕ регистр/пара регистров — `size = 2`.

```python
if mnemonic in _mnemonics:
    opcode, fmt, size = _mnemonics[mnemonic]
    # ALU r: immediate form is 2 bytes, not 1
    if fmt == 'r' and operand:
        op_u = operand.strip().upper()
        if op_u not in ('A','B','C','D','E','H','L','M','BC','DE','HL','PSW'):
            size = 2
    location += size
    self.pc = location
```

ВАЖНО: та же логика должна быть и в pass 2 (где реально эмитятся байты) — проверить, что pass 2 уже корректно кодирует imm-форму в 2 байта (скорее всего да, т.к. байты эмитятся правильно, а ломается только pass 1). Если pass 2 тоже берёт size из таблицы — поправить аналогично.

### Проверка фикса
После фикса пересобрать рантайм-объекты (`test_crun.obj`, `test_crun_nostart.obj`) этим же ассемблером и прогнать 97 тестов. Ожидаемо: `t27` -> PASS, `t24` перестаёт зависать на 0x0038 (результат может остаться неверным из-за отдельной логики 64-bit — это уже рантайм, не ассемблер).

## БАГ #2 (СРЕДНИЙ): однобуквенные метки конфликтуют / не разрешаются (LINK_FAIL)

### Суть
Тесты `t41`, `t43`, `t43b` (`.s`-фрагменты с `main`) используют глобальные переменные-однобуквенки:
- t41: `shld i`, `shld n`  -> линкер: `Unresolved symbol: I`, `N`
- t43: `shld x`, `shld y`  -> `Unresolved symbol: X`, `Y`
- t43b: `shld a`, `shld b`, `shld c` -> `Unresolved symbol: A`, `B`, `C`

Ассемблер капсит метки в ВЕРХНИЙ регистр (`i`->`I`, `a`->`A`, ...). Это само по себе не баг. Проблема в том, что в этих `.s` **секция данных пуста** — определения `i:/n:/x:/y:/a:/b:/c:` с `.dw 0` отсутствуют:

```
        .area  SMALLC_GENERATED_DATA  (REL,CON,DSEG)
        .globl main
; (пусто — нет i:, n: и т.д.)
```

### Классификация
Это **в первую очередь проблема тестовых данных** (неполные `.s`), а не ассемблера: ассемблер корректно помечает `I/N/X/Y/A/B/C` как external/import, линкер честно сообщает об неразрешённом символе.

### Что проверить в i8080_ci (чтобы исключить баг)
1. Убедиться, что если в `.s` ЕСТЬ определение `i:` (даже однобуквенное) в DSEG, то ассемблер создаёт символ `I` и линкер его разрешает (т.е. каппинг не ломает match между определением и ссылкой). Прогнать минимальный кейс:
   ```
   main:
       lxi h,#1
       shld i
       ret
   i:
       .dw 0
   ```
   Ожидаемо: линкуется, `I` разрешён.
2. Убедиться, что однобуквенные метки не путаются с регистрами при **определении** (метка `a:` не должна трактоваться как регистр A).

Если п.1/п.2 проходят — баг #2 закрывается добавлением определений данных в тестовые `.s` (со стороны SmallC/тестов), i8080_ci менять не нужно.

## НЕ баги i8080_ci (для полноты картины — не чинить в ci-app)
- `t25`, `t25c` (exit=1), `t44` (exit=3) — variadic `va_arg` / integer promotion. Это компилятор cc8080 (stack offsets), не ассемблер.
- `t26` (exit=62723), `t45` (exit=53237) — float/double арифметика. Это рантайм (ccfadd/ccfmul/ccdadd/...) или компилятор, не ассемблер.
- `t24` после фикса #1 может остаться с неверным результатом — это логика 64-bit в рантайме, не ассемблер.

## Итог для ci-app
Приоритет — **БАГ #1** (ALU imm size в pass 1). Он один объясняет t27 и зависание t24, и бьёт по любому модулю с ALU-imm инструкциями. БАГ #2 — проверить на минимальном кейсе; скорее всего чинится на стороне тестов.
